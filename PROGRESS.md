Ramulator 2.1 facts that matter later (verified this session):

- Configs are Python scripts; DRAM standards are Python DSL classes under
  `python/ramulator/dram/`; C++ under `src/ramulator/dram/impl/` is generated.
  A build regenerates those files, so the submodule shows them as modified.
- HBM3 hierarchy in Ramulator: Channel > PseudoChannel > Sid > BankGroup > Bank
  > Row > Column. One controller = one channel = 2 pseudo channels.
- Native access is 32 bytes (BL8 on a 32-bit pseudo channel). Frontends must
  send `size_bytes` equal to that.
- Ramulator simulates HBM3 in half-CK ticks (312.5 ps) because ACT occupies
  1.5 CK and PRE/REF 0.5 CK on the command bus. Constraint latencies are
  adjusted by the command lengths: measured ACT to RD is 63 ticks, not 62;
  ACT to PREpb is 92, not 90; PREpb to ACT is 50, not 52. Our core must model
  this to match cycle-exactly (or we compare at CK tolerance).
- Internal `tCK_ps` is `625 // 2 = 312`, so Ramulator's own ns and MBps stats
  read 0.16% high. Convert ticks ourselves with 312.5 ps.
- The simulation stops when the frontend has SENT its last request; the ~32
  requests still queued are never served. Compare on served counts, or add a
  draining frontend in Phase 4.
- `LoadStoreTrace` loads the whole `LD/ST <addr>` file into memory and replays
  once. `ReadWriteTrace` takes pre-mapped address vectors (bypasses the
  mapper), useful to test our mapper and timing separately.
- `tests/device_timings/harness.DeviceUnderTest` lets us ask the device model
  "when is command X legal" one command at a time. `CmdTraceRecorder` plugin
  records every issued DRAM command with its tick. Both are the Phase 4 diff
  tools.
- Address mapper `RoBaRaCoCh` for HBM3 puts, above the 5 column bits (32
  accesses x 32 B = 1 KB row), in order: PseudoChannel, Sid, BankGroup, Bank,
  Row. Consecutive accesses therefore stay in one bank and pay tCCD_L.

## Open questions to settle at the start of Phase 1

1. **Request size: 32 B or 64 B?** The task text says 64-byte requests, but an
   HBM3 pseudo channel access is 32 B, which is also why GPUs use 32 B L2
   sectors. Recommendation: generate at 32 B natively with a `request_bytes`
   knob; a 64 B request is then two adjacent 32 B accesses.
2. **How much memory do we model?** One HBM3 stack is 16 GB and 819 GB/s. A
   70B fp16 model (140 GB) does not fit. Options: (a) model N stacks as N x 16
   channels, (b) choose a "large" model whose fp16 weights plus KV fit, (c)
   simulate a representative slice (decode traffic repeats per layer).
   Recommendation: 16-channel stack as the unit, `stacks` knob, large model =
   a tensor-parallel shard that fits, validation against Ramulator on a
   2-layer slice.
3. **Trace size and format.** A 16 GB decode step is 500 M requests of 32 B; a
   text trace is tens of GB and Ramulator holds the trace in RAM. Options:
   compact binary records, or a segment list (base, count, stride) expanded
   identically in Python and C++, with text export only for validation slices.
4. **Model configs.** Small: something like a 1B-class model. Large: see 2.
   Need real published shapes (layers, hidden, heads, KV heads, intermediate).
